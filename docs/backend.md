# Backend contract

The backend is implemented in `functions/src/`, with browser-safe Zod contracts in `shared/src/` and the React frontend in `web/src/`. All callable names below are exported from `functions/src/index.ts`, in `asia-southeast1`.

Use Google Firebase Authentication and Firebase callable POST requests. Send `{}` for actions without fields. Production requires App Check and `APP_ORIGINS`; local Emulators disable App Check only for local development. Each action re-verifies the ID token with revocation checking, validates a strict schema, and applies a distributed per-account/action rate limit.

## Callable actions

| Action | Input, excluding common `requestId` | Result |
| --- | --- | --- |
| `getTeacher` | `{}`; no request ID | Profile from verified Google identity; saves basic account data |
| `getRetention` | `{}`; no request ID | Current school year, three retained years, expiry notice within 30 days |
| `saveSubject` | `name` | Saved subject ID and name |
| `createClass` | `year`, `term` (1 or 2), `subject`, `group` | Class ID, context, version and roster version |
| `addStudent` | `classId`, `number`, `name` | Stable student ID, public code and version |
| `updateStudent` | `classId`, `studentId`, `expectedVersion`, `number`, `name`, `confirmNumberChange` | Updated student, version, `qrReplaced` |
| `setStudentActive` | `classId`, `studentId`, `expectedVersion`, `active`, `confirmed: true` | Student and new version |
| `importStudents` | `classId`, `expectedRosterVersion`, `rows: [{number, name}]` | Added/changed/unchanged counts and new roster version |
| `createTask` | `classId`, optional `name` | Task ID, name, order, version |
| `renameTask` | `classId`, `taskId`, `expectedVersion`, `name` | Task ID, name and version |
| `deleteTask` | `classId`, `taskId`, `expectedVersion`, `confirmed: true` | Task ID and `deleted: true` |
| `resolveQr` | `payload`; no request ID | Student/class details and newest-first tasks with statuses, dates and `selectable` |
| `getQrData` | `classId`, optional `studentId`; no request ID | Current QR payloads and card labels, active students only, ordered by number |
| `saveWork` | `payload`, sent `status` | Status, UTC saved time, version; no student/class/task details |
| `savePastWork` | `payload`, `taskId`, sent `status`, `confirmed: true` | Status, UTC saved time, version |
| `getWork` | `classId`, `studentId`, `taskId`; no request ID | Status, saved time or null, version including cleared-work history |
| `changeWorkStatus` | `classId`, `studentId`, `taskId`, `expectedVersion`, `status`, `confirmClear` | Status, saved time or null, new version |
| `getRequestResult` | Original `requestId` | `{state: 'unknown'}` or `{state: 'confirmed', action, result}` |

Mutation request IDs are UUIDs generated by the caller before sending. Reuse the original ID and unchanged input after a lost reply. A completed request returns its original result even if a new task exists or the recorded work was later cleared. Reusing an ID with different normalized input or another action is rejected. An unknown result alone does not prove that an in-flight request failed; stop new scans, query again, and retry only with the original ID/data.

Statuses are machine values: `not-sent`, `on-time`, `late-1` through `late-4`. Scanning accepts sent statuses only. Thai labels are exported as `STATUS_LABELS` from shared. Times are ISO UTC strings from the backend; the UI displays `Asia/Bangkok`. No client date is accepted.

Names are trimmed plain text of 1–200 characters. Student numbers are positive integers up to 999999; digit strings such as `01` normalize to 1. IDs cannot contain path separators. Imports accept 1–200 reviewed rows and reject duplicate normalized numbers. Excel file parsing, formula detection in original files, camera control, sound, PDF generation and browser pending-request persistence are implemented in the frontend.

## Firestore layout and reads

```text
teachers/{uid}                         profile
  subjects/{subjectId}                 reusable subjects
  classes/{classId}                    immutable class context, rosterVersion, latestTaskId
    students/{studentId}              number, name, active, version, currentQrId, publicCode
    tasks/{taskId}                    name, order, version, createdAt
    work/{pairHash}                   current sent status, savedAt, version
    workVersions/{pairHash}           persistent version counter, including clears
  requestResults/{requestId}          action fingerprint and confirmed result
  auditEntries/{requestId}            old/new values, affected IDs, server time
  rateLimits/{action}                 request count and reset time
qrTokens/{payloadHash}                current/replaced QR, owner and related IDs
```

### ความสัมพันธ์ของแต่ละ collection

โครงสร้างหลักคือ ครูเป็นเจ้าของห้องเรียน ห้องเรียนมีนักเรียนและชิ้นงาน และรายการส่งงานเชื่อมนักเรียนหนึ่งคนกับงานหนึ่งชิ้น ปีการศึกษาและภาคเรียนเป็นฟิลด์ใน `classes` ไม่ได้มี collection แยก

| Collection | เก็บอะไร | เชื่อมกับอะไร | ความสัมพันธ์และหน้าที่ |
| --- | --- | --- | --- |
| `teachers` | ชื่อ อีเมล รูป และ `ownerId` ของครู | ใช้ Firebase Auth UID เป็น ID; เป็นเอกสารแม่ของ `subjects`, `classes`, `requestResults`, `auditEntries` และ `rateLimits` | ครูหนึ่งคนมีหลายวิชาและหลายห้อง ข้อมูลใต้ path ของครูแยกจากบัญชีอื่น |
| `subjects` | ชื่อวิชาที่ครูบันทึกไว้และ `ownerId` | อยู่ใต้ครู; `classes.subjectId` ชี้ถึงวิชาในบัญชีเดียวกัน | วิชาหนึ่งใช้สร้างหลายห้องได้ เช่น ต่างปี เทอม หรือกลุ่ม ชื่อวิชายังคงอยู่เมื่อข้อมูลห้องหมดอายุ |
| `classes` | ปี เทอม วิชา กลุ่ม `subjectId`, `latestTaskId`, `rosterVersion`, `version` และวันหมดอายุ | อยู่ใต้ครู; เชื่อมวิชาด้วย `subjectId` และงานล่าสุดด้วย `latestTaskId`; เป็นเอกสารแม่ของ `students`, `tasks`, `work` และ `workVersions` | หนึ่งห้องหมายถึงหนึ่งปี + เทอม + วิชา + กลุ่มของครู ห้องมีนักเรียนและงานหลายรายการ `rosterVersion` ใช้ตรวจว่ารายชื่อเปลี่ยนหลังเปิดฟอร์มหรือ review Excel หรือไม่ |
| `students` | เลขที่ ชื่อ `active`, `version`, `publicCode`, `currentQrId` และข้อมูลหมดอายุ | อยู่ใต้ห้อง; `work.studentId` เชื่อมรายการส่งงาน และ `currentQrId` ชี้เอกสารใน `qrTokens` | เป็นรายการนักเรียนในห้องนั้น ใช้ `studentId` เดิมเมื่อเปลี่ยนชื่อหรือเลขที่ จึงรักษาประวัติส่งงานได้ คนเดียวกันที่เรียนหลายห้องมีรายการนักเรียนแยกกัน |
| `tasks` | ชื่องาน ลำดับ เวลาสร้าง `version` และข้อมูลหมดอายุ | อยู่ใต้ห้อง; `work.taskId` เชื่อมรายการส่งงาน และ `classes.latestTaskId` ชี้งานล่าสุด | ห้องหนึ่งมีงานหลายชิ้น งานหนึ่งมีนักเรียนส่งได้หลายคน สแกนปกติบันทึกลงงานล่าสุด ลบงานได้เฉพาะเมื่อไม่มีรายการส่งปัจจุบันเหลือ |
| `work` | `studentId`, `taskId`, สถานะ วันที่ส่ง `version` และข้อมูลหมดอายุ | เชื่อมนักเรียนกับงานภายในห้องเดียวกัน; ID เป็น hash ของคู่ `studentId` + `taskId` | นักเรียนหนึ่งคนส่งหลายงานได้ และงานหนึ่งมีหลายคนส่ง แต่หนึ่งคู่มีรายการส่งปัจจุบันได้เพียงรายการเดียว ไม่มีเอกสารหมายถึงยังไม่ส่ง การเปลี่ยนเป็นยังไม่ส่งลบเอกสารนี้และวันที่ส่ง |
| `workVersions` | `studentId`, `taskId`, เลข version และข้อมูลหมดอายุ | อยู่ใต้ห้องและใช้ ID ของคู่นักเรียน–งานเดียวกับ `work` | เก็บ version ต่อแม้ลบ `work` แล้ว เพื่อป้องกันฟอร์มเก่าเขียนทับหลังมีการส่ง ล้าง และส่งใหม่ อ่านผ่าน `getWork` |
| `requestResults` | ชนิด action, fingerprint ของคำขอ ผลที่ยืนยันแล้ว เวลา ปี และวันหมดอายุ | อยู่ใต้ครู; ใช้ `requestId` เดียวกับคำขอบันทึกและเอกสาร audit ของคำขอนั้น | หนึ่งคำขอบันทึกที่สำเร็จมีผลหนึ่งรายการ Retry ด้วย ID และข้อมูลเดิมคืนผลเดิมโดยไม่ทำซ้ำ ใช้ตรวจผลเมื่อคำตอบหายระหว่างทาง |
| `auditEntries` | ผู้ทำ action เวลา ปี ค่าเดิม/ค่าใหม่ และ ID ที่เกี่ยวข้องใน `changes` | อยู่ใต้ครู; ID เป็น `requestId`; `changes` เชื่อมห้อง นักเรียน งาน หรือวิชาตามชนิด action | เก็บประวัติของคำขอบันทึกที่สำเร็จ พร้อมกับข้อมูลและผลคำขอใน transaction เดียว ประวัติยังอยู่หลังล้างสถานะหรือลบงาน และหมดอายุตามปีที่เกี่ยวข้อง |
| `rateLimits` | จำนวนคำขอ `resetAt` และ `expiresAt` | อยู่ใต้ครู; ใช้ชื่อ action เช่น `saveWork` หรือ `importStudents` เป็น ID | ครูแต่ละคนมีตัวนับแยกตาม action ใช้จำกัดความถี่คำขอ ข้อมูลนี้มีวันหมดอายุของตัวเองและไม่ได้ผูกกับปีการศึกษาของห้อง |
| `qrTokens` | QR payload, `publicCode`, `ownerId`, `classId`, `studentId`, สถานะ `current`/`replaced` และข้อมูลหมดอายุ | อยู่ระดับบนสุด; เชื่อมครู ห้อง และนักเรียน ส่วน `students.currentQrId` ชี้กลับมายัง QR ปัจจุบัน | ค้นจาก hash ของ QR ก่อนรู้ว่าต้องเปิดห้องใด แล้วตรวจเจ้าของและสถานะ นักเรียนหนึ่งรายการมี QR หลายรายการในประวัติ แต่ใช้ได้เฉพาะ QR ปัจจุบันของนักเรียนที่เปิดใช้งาน |

ตัวอย่าง: ห้องคณิตศาสตร์ ม.1/1 มีนักเรียน 30 คนและงาน 3 ชิ้น จึงมีคู่ที่อาจส่งงานได้ 90 คู่ แต่สร้าง `work` เฉพาะคู่ที่ส่งแล้ว ถ้าสมชายส่งงานชิ้นที่ 3 เอกสาร `work` จะเก็บ `studentId` ของสมชายและ `taskId` ของงานชิ้นที่ 3

เมื่อเปลี่ยนเลขที่ของสมชาย `studentId` เดิมยังคงอยู่ ทำให้ `work` เชื่อมประวัติได้เหมือนเดิม ระบบทำเครื่องหมาย QR เดิมเป็น `replaced` สร้าง QR ใหม่ และเปลี่ยน `students.currentQrId` ไปชี้รายการใหม่ การเปลี่ยนชื่อเพียงอย่างเดียวไม่เปลี่ยน QR

Rules allow the Google-authenticated owner to read their profile, subjects, retained classes and their students/tasks/current work. All browser writes are denied. QR tokens, work version counters, request results, audits and rate limits are backend-only. Open a work-status form through `getWork` to obtain a current version even when no current work document exists.

Class list queries must filter `year` and `term`; an unrestricted query across retained and expired years is denied. Student lists can query `active == true`. Summary can read work and tasks within its selected class. The frontend keeps browser persistent caching disabled.

Class IDs and subject IDs are hashes of normalized names/context, scoped by teacher. Student and task IDs are random stable UUIDs. QR payloads include a public class/student-number code plus a random 256-bit token, and never include student names. Renumbering invalidates the previous token; a name change leaves it current. Turning a student off reserves their number and retains work.

Student edits and imports serialize through the class roster version. Task creation serializes through the class document. Work changes use a persistent pair revision to prevent stale forms from overwriting records after a send/clear/re-send cycle. Every mutation writes its data, request result and audit in one transaction. A scan never creates tasks or overwrites existing sent work.

## Errors and limits

Callable errors use Thai messages with `details.reason`, such as `VERSION_CONFLICT`, `ALREADY_SENT`, `NO_TASK`, `QR_REPLACED`, `STUDENT_INACTIVE`, `QR_WRONG_OWNER`, `YEAR_UNAVAILABLE`, `REQUEST_REUSED` and `RATE_LIMIT`. Duplicate work errors include only its previous status/date/version; no other teacher's details are exposed. Validation errors include field paths, not input values. Internal errors return a correlation ID without stack traces.

Rates are 120/minute per teacher/action for scanning, QR resolution and result lookup; 6/minute for imports; 30/minute for other actions. Throttling returns `retryAfterSeconds`. Request data is capped at 256 KiB. QR/history/download read actions return at most 1000 records and explicitly reject larger results. These limits need measurement against the planned production load; they are not claimed load-test results.

## Expiry

The school year changes on May 1 at midnight in Bangkok. Access and mutations are blocked outside the current and previous two school years, before physical cleanup runs. The scheduled function runs daily at 00:05 Bangkok time and removes expired classes recursively, then independently cleans expired students, tasks, work, revisions, QR, requests and audits. Each child has year/expiry metadata so cleanup can resume after a parent was already deleted. Repeated cleanup is safe. Teacher profiles and reusable subjects remain.

Backups, restore procedures, production App Check metrics, billing alerts and load measurement still require operator setup; no production deployment or cloud resources were created by this implementation.

## Teacher plans

The plan implementation is specified by `model-plan.md`. `getPlanSummary` returns the effective plan and the current Buddhist school year's usage across both terms. `previewPlanCode` takes `code`; `redeemPlanCode` takes `requestId`, `code` and the returned `previewToken`. A stale preview raises `PLAN_PREVIEW_CHANGED` with the new preview, requiring another confirmation. All request and response contracts live in `shared/src/schemas/plan.ts`.

`createClass` accepts the current school year only and checks plan expiry and yearly usage transactionally. `deleteClass` takes `requestId`, `classId` and the exact displayed `confirmationName` (`subject · group`). Its response marks deletion accepted; cleanup runs separately. Normal service access and browser Rules reject deleting classrooms immediately. Browser classroom lists must filter `status == active`, alongside year and term. Direct reads treat a missing status as active.

Subscriptions live under `teachers/{uid}/subscription/current`, usage under `classroomUsage/{schoolYear}`, and plan history/results under `planEvents` and `planRequests`. Hash-keyed `planCodes` and `classroomDeletionJobs` are server-only. Minimal `classDeletionRequests` receipts survive cleanup to prevent an old retry from deleting a replacement classroom. No browser can directly write any of these records. Admin operations are terminal-only and use trusted service-account credentials; see [teacher-plans.md](teacher-plans.md).
